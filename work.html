Current study

Agent-led malware analysis for Sigma rules

My thesis. Does an AI agent that chooses its own next analysis step write Sigma rules that catch more malware, with fewer false alerts, than a fixed workflow using the same tools? Approved in October 2026. No results yet.

Malware AnalysisSigmaAI AgentsDetection Engineering

The constraint

Generating detection rules with a language model is no longer new. Recent work already turns threat reports and sandbox output into Sigma rules, the vendor-neutral format for detections over log events, and tests them against variants and benign activity. A thesis that only generates rules would repeat that work.

The question I am testing is narrower: whether the analysis steps matter. Packed malware hides its behavior in the file on disk, so what an analyst learns depends on what they do next, such as unpacking it, dumping memory, or running it again. An agent can choose those steps. A fixed workflow runs the same ones every time.

The decision

Compare two workflows that differ only in who picks the analysis steps. Both get the same model, the same rule writer, the same tool menu, and the same resource ceiling. One follows a sequence frozen on development samples. The other lets an agent choose the next step and records each question, action, result, and decision to stop.

Sigma is the main output, written from recorded endpoint activity. YARA rules come second, and only where a specific file or memory artifact supports one. Every behavior claim and every rule condition links back to the event records that support it.

Existing rules and deterministic templates run as controls, so a gain has to beat what simple generation from the same evidence already achieves.

What I rejected

Starting by building a general-purpose analysis agent. It is the obvious first step and the wrong one here, because an agent with no fixed baseline beside it cannot show that its choices helped. The plan starts with one reproducible case, then a pilot of 10 to 20 files, and adds adaptive tool choice only after the fixed workflow works.

Counting rules that parse as success. A rule that is valid YAML can still match nothing, or match everything. Each rule has to compile, run against real event records, and be checked against benign activity before it counts.

Treating unpacking as the goal. Unpacking is one way to gather evidence, and the result that matters is whether the rule it leads to detects anything.

How I would know it worked

Detection on malware the rules never saw. Rules are written from one set of samples, frozen, then replayed on a sealed set from different payload groups. Related copies stay on the same side of that split, so a repacked copy of a development sample cannot pass as a new one.

False alerts on benign workloads, measured alongside detection. A rule that fires on routine administration costs an analyst more time than it saves.

Behavior accuracy against independently reviewed labels, plus failures, abstentions, and machine cost. If the fixed workflow writes equally useful rules for less, that is a result, and I will report it as one. Engineer review time comes later, as a separate study, and only if the technical results justify it.

Exploratory lab study

Evaluating autonomous pentest agents

An exploratory study of autonomous pentest agents on intentionally vulnerable lab targets, with recorded outcomes, detection coverage limits, and API spending.

AI AgentsDetection EngineeringIsolated Lab

The constraint

I studied how an autonomous pentest platform uses its tools, follows scope restrictions, and reports results against intentionally vulnerable targets. I also checked what the detection rules bundled with the platform could observe.

The lab changed during the investigation. Models, context settings, task permissions, and inherited findings varied. These runs support observations about those configurations, but do not isolate model capability as the cause of every difference.

The decision

Use a lab with a controlled external boundary and deliberately vulnerable targets. Internal segmentation was part of the test environment. Local inference and API inference were separate configurations; API access used a restricted relay.

Run local model profiles and an API model on Metasploitable2, then expand to a segmented lab. Preserve task goals, activity, findings, and account-balance snapshots where the capture harness was used.

Place Suricata on the analysis VM’s target-facing interface with the bundled rules. That sensor did not monitor the internal switch. The rules mainly identified the tool’s HTTP User-Agent strings; this was not a benchmark of general intrusion detection.

What I rejected

Treating a restricted task as a security verdict. Task 20 inherited an existing foothold and prohibited further escalation and lateral exploitation. Later tasks allowed more actions and inherited earlier findings. Their different outcomes do not form a controlled prompt-only comparison.

Counting every reported finding as a verified vulnerability. The records mix identification, demonstrated access, and pending findings. Without consistent adjudication and deduplication, the counts cannot establish precision or a model ranking.

Observations and limits

The investigation report lists 4 findings for each of two local profiles and 22 for the API configuration before further follow-up findings. These are reported counts across different task histories, not independently adjudicated unique vulnerabilities from repeated matched trials.

The later assessment notes describe privilege escalation and lateral access during an approximately three-hour autonomous task. Those tasks’ raw database records are not exported in the repository reviewed for this page. I distinguish these documented observations from the captured runs.

The detection report records one alert from a manual signature test before the assessment tasks. It reports no alerts from the subsequent runs under those rules. The narrow rule scope and unmonitored internal segment prevent a recall estimate or a conclusion about general detection effectiveness.

Account snapshots show a $0.12 decrease during task 19 and $0.08 during task 20. The later notes report about $9.13 consumed from the initial $10 credit across the investigation. These are API account-balance changes, excluding local compute, setup, and review; delayed charges prevent exact per-task billing.

Multi-tenant SIEM architecture

Three SIEM platforms across more than 30 government-contractor clients, each chosen for the estate it had to monitor, all feeding one alert queue.

SIEMDetection EngineeringGCC HighKafka

The constraint

An MSSP with more than 30 SOC customers, all government contractors under CMMC. The estates had almost nothing in common: different services, different architectures, different sites, and devices we did not own. A conventional SOC structure assumes one estate, and there were thirty.

GCC High added a limit of its own. Its management APIs lag the commercial tenant and use different URLs and parameters, so tooling that works against commercial Microsoft does not necessarily work there at all.

The decision

Three platforms, chosen per client rather than one standard, behind a single alert surface.

Sentinel took the GCC High cloud workloads, ingesting through log forwarding, Event Hubs, Defender, and connectors I built for Microsoft XDR, with Azure Arc and the Azure Monitor Agent extending reach to machines outside the tenant. On-premises servers and firewalls went through a local Kafka platform that normalized before writing to an analytics bucket, with syslog split to its own.

AlienVault took the clients outside full FedRAMP scope who were not running SentinelOne. That one is almost entirely agent-based, with API integrations to Azure, FortiGate and whichever EDR the client had, and on-premises sensors forwarding network and firewall data over HTTPS.

SentinelOne took the clients already using it for EDR. I wrote parsers and translators into its parsing engine in regex and JSON, covering whatever applications a client asked for, fed from endpoint agents and a Scalyr agent on a hardened central server. Everything was normalized before it reached the data lake.

Detection was written per platform, as analytics and fusion rules in Sentinel and STAR rules against the SentinelOne lake. One API then polled all three for alerts in near real time and pushed them into the SOC dashboard in our PSA tool, so an analyst worked a single queue.

What I rejected

Standardizing on one SIEM and fitting every client to it. That is cheaper to run and it was the wrong answer here, because the estates differed in exactly the ways that decide the tool.

A cloud-native GCC High tenant, a site of on-premises firewalls with no cloud presence, and a client with SentinelOne already deployed are three different ingestion problems. Retrofitting one platform across all three means paying for the mismatch in every environment instead of choosing once per client. Architecture, tooling and scope should follow the environment rather than the other way around.

How I would know it worked

Alert latency from source to dashboard, and how long a new client took to stand up.

SentinelOne and AlienVault delivered under a minute. GCC High Sentinel delivered under five in these deployments. Those are operational observations from this design, not latency guarantees for the platforms.

A new client was onboarded in under a week, gated by their own IT team rather than by us. That figure is the real test of choosing per client: a bespoke architecture is only affordable if standing one up is routine, so every deployment was scripted and staged in advance, maintenance scripts included.

Underneath both, one criterion. An analyst worked a single queue, and if the platform behind an alert changed how they triaged it, the architecture had failed.
